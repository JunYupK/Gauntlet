## 1. 개요

봇들이 트론 라이트사이클로 겨루고, 세대를 거치며 코드 재작성으로 개선되는 시스템.

사내 CoP 발표용 데모이며 전하려는 메시지는 하나다 — **"하네스와 루프를 갖추면 개발이 이만큼 빨라진다."** 따라서 최종 결과물이 아니라 만들어진 과정이 주인공이고, 설계의 모든 판단은 이 목적에 종속된다.

### 1.1 시스템의 두 영역

경계선은 **봇 코드가 파일로 확정되는 순간**이다.

| 영역 | 무엇 | 성질 |
|---|---|---|
| **하네스 밖** | Claude Code 같은 CLI 에이전트가 봇 코드를 작성 | 비결정론. 몇 번을 다시 써도 무방 |
| **하네스 안** | 엔진 · 관문 · 대전 · 진단 · 리플레이 생성 | **완전 결정론. LLM을 일절 호출하지 않는다** |

LLM 호출은 비결정론이다. 이를 하네스 안에 넣으면 R1이 무너지고, R1이 무너지면 루프의 판정이 흔들려 C2가 성립하지 않는다.

## 2. 게임 규칙

30×30 정수 격자 위 1:1 트론 라이트사이클. 지나간 칸은 영구 벽이 되고, 먼저 부딪히는 쪽이 진다.

### 2.1 턴 판정 — 순서 의존성 없음

턴 `t`의 벽 집합 `W(t)`를 **고정한 채로** 두 봇의 목표 좌표 `pA`, `pB`를 각각 계산한 뒤 동시에 판정한다.

```
A 사망  ⟺  pA ∉ 격자  ∨  pA ∈ W(t)  ∨  pA == pB
B 사망  ⟺  pB ∉ 격자  ∨  pB ∈ W(t)  ∨  pB == pA

W(t+1) = W(t) ∪ { 생존한 봇의 새 머리 좌표 }
```

A와 B를 바꿔도 결과가 같으므로 선후공 이점이 존재하지 않는다.

### 2.2 부수 규칙

| 항목 | 규칙 |
|---|---|
| 시작 칸 | 0턴에 즉시 벽. 따라서 **후진은 별도 규칙 없이 자기 벽 충돌로 자연 사망** |
| 승패 | 한쪽만 사망 → 생존 승 / 양쪽 사망 → 무승부 |
| 종료 보장 | 매 턴 벽이 최소 1칸 늘어나므로 **최대 턴 ≤ 900** |
| 좌석 교대 | 같은 시드의 두 위치 `(P1, P2)`에 대해 1판 `A@P1 vs B@P2`, 2판 `B@P1 vs A@P2`. **위치는 그대로, 앉는 봇만 바꾼다** (미러링이 아니다) |

### 2.3 시드 → 시작 배치

```
· 가장자리에서 최소 3칸 안쪽        (어느 방향이든 최소 3턴 생존 보장)
· 두 위치 간 맨해튼 거리 ≥ 10       (초반 즉시 접촉 방지)
· 초기 방향은 시드에서 4방향 균등
· 심사 시드 = 1‥50,  홀드아웃 시드 = 1001‥1050
```

심사 시드는 에이전트에게 공개하고, 홀드아웃 시드는 노출하지 않는다. 두 승률의 격차가 곧 시드 과적합 신호다.

## 3. 봇 계약

```java
public interface Bot {
    String name();
    Direction move(GameView view);
}

public record GameView(
    int width, int height,
    boolean[][] wall,          // 이동 전 벽 집합 W(t)
    Point myHead,  Direction myDir,
    Point oppHead, Direction oppDir,
    int turn
) {}

public enum Direction { UP, DOWN, LEFT, RIGHT }
```

**봇은 무상태 순수 함수다.** 인스턴스 필드를 가질 수 없으며, 이는 G2가 리플렉션으로 기계 판정한다. 이 제약으로 "같은 입력 → 같은 출력"이 인터페이스 수준에서 강제되어, R1이 규율이 아니라 구조가 된다.

봇은 전지 시점을 갖는다 — 전체 격자, 양쪽 머리와 방향, 턴 번호. 히스토리는 제공하지 않는다(무상태와 일관).

봇은 `arena-core`의 `GameView`와 `Direction`만 볼 수 있다. 엔진 내부도, 관문 구현도, 상대 봇도 타입 시스템상 접근할 수 없다.

## 4. 관문 (C1)

`G1 → G7` 순서로 실행하고 **첫 실패에서 즉시 중단**한다. 비용 순서와 피드백 속도가 같은 방향이다.

| | 관문 | 판정 방법 | 합격 조건 | 반려 시 산출물 |
|---|---|---|---|---|
| G1 | 컴파일 | `compileJava` | 에러 0 | 컴파일러 메시지 원문 |
| G2 | 무상태 | 리플렉션 `getDeclaredFields()` | non-static 필드 0개 | 위반 필드명 목록 |
| G3 | 금지 API | ASM 바이트코드 스캔 | 위반 명령 0개 | 클래스·메서드·라인 위치 |
| G4 | 합법 수 | 국면 10,000개 퍼징 | 예외 0 · null 0 · 4방향 외 반환 0 | 최소 반례 국면 |
| G5 | 결정론 | ① 같은 국면 2회 호출 비교 ② 베이스라인 3종 상대 심사 시드 경기를 2회 실행해 리플레이 해시 대조 | 양쪽 100% 일치 | 불일치 국면 또는 해시 |
| G6 | 시간 예산 | 국면 10,000개 벤치 | p99 < 5 ms | 실측 p50/p99 |
| G7 | 회귀 방지 | 베이스라인 3종 대전 | **패배 0회** | 패배한 시드와 진단 |

### 4.1 G3 금지 목록

R1을 깨뜨릴 수 있는 것 전부다.

```
시드 없는 난수   Math.random(), new Random()      // 시드 있는 Random은 허용
시계             System.currentTimeMillis/nanoTime, java.time.*
동시성           Thread, ExecutorService, ForkJoinPool
외부 세계        java.io.*, java.nio.file.*, java.net.*
전역 가변 상태   non-final static 필드, final이어도 가변 객체
우회             java.lang.reflect.*, Unsafe
```

### 4.2 G6에 대해 — 대전은 시간에 의존하지 않는다

시간 기반 타임아웃은 R1을 깨뜨린다. 같은 봇이 어떤 실행에서는 통과하고 어떤 실행에서는 타임아웃되면 같은 조건에 다른 결과가 나온다.

따라서 **성능은 G6에서만 판정하고, 대전 중에는 어떤 시간 제한도 걸지 않는다.** G6를 통과한 봇의 대전 결과는 순수하게 결정론이다.

### 4.3 G7에 대해 — "전승"이 아니라 "패배 0회"

`RandomBot` 상대로는 정면 충돌 무승부가 구조적으로 발생한다. 전승을 요구하면 실력과 무관하게 반려되므로, 무승부는 허용하고 패배만 금지한다.

### 4.4 관문에 넣지 않은 것 — 품질 기준

관문을 세게 잡을수록 R3이 손해를 본다. R3은 초기 세대가 처참하게 약할 것을 요구하는데, "자멸하지 말 것" 같은 품질 관문을 걸면 Gen 1부터 이미 벽을 피해 개선 곡선의 가장 극적인 구간이 관문에 먹힌다.

따라서 **자멸률은 반려 사유가 아니라 세대별로 측정해 남기는 지표**다(§8). 그리고 **Gen 0은 관문 대상이 아니다** — Gen 0은 사람이 심는 기준선이고 루프는 Gen 1부터 돈다.

### 4.5 하네스의 문서 쪽 얼굴

C1은 규칙과 관문이 **문서와 코드**로 존재할 것을 요구한다. 코드 쪽은 `arena-gate`, 문서 쪽은 저장소 루트의 **`CLAUDE.md`(봇 작성 규칙서)** 다. 에이전트가 지켜야 할 계약, 금지 사항, 제출 절차를 여기에 명시한다.

**관문에서 반려된 항목은 규칙서에도 반영해, 문서와 관문이 같은 것을 말하도록 유지한다.**

## 5. 루프 (C2)

```
Gen N 챔피언
   │
   ├─▶ 에이전트가 Gen N+1 도전자 코드 작성 (직전 챔피언에서 증분 개선)
   │      │
   │      ├─▶ 관문 G1~G7  ──반려──┐
   │      │        │              │
   │      │      통과             │  반려 사유(기계 판정 결과)를
   │      │        │              │  근거로 재작성
   │      └─▶ 챔피언전 100경기 ───┤
   │               │              │
   │        60% 미만 ─────반려────┘
   │               │
   └───── 60% 이상 → 승격 → Gen N+1 챔피언
```

- 재시도 한도는 **세대당 5회**. 초과하면 실험을 종료하고 `CONVERGED`로 선언한다.
- 반려된 시도는 코드를 포함해 **전부 남긴다**(§8).
- 에이전트는 매 세대 백지에서 쓰지 않고 **직전 챔피언을 출발점으로 증분 개선**한다. 세대별 diff가 작고 선명해야 "이번 세대는 무엇을 배웠는가"가 한 문장으로 설명된다.

### 5.1 에이전트가 쓰는 명령

```bash
./gradlew gate      --bot=Gen07Bot   # 관문 G1~G7 → JSON 리포트
./gradlew challenge --bot=Gen07Bot   # 챔피언전 100경기 → 승격 판정 + 진단 리포트
./gradlew record                     # 발표 번들 생성
./gradlew record --verify            # 전체 재실행 후 리플레이 해시 대조 (R1 검증)
```

이 넷이 하네스의 전부다. 에이전트는 봇 코드를 쓰고 이것만 실행한다.

## 6. 승격 심사

| 항목 | 값 |
|---|---|
| 심사 규모 | 시드 50개 × 좌석 교대 = **100경기** |
| 무승부 | **0.5점** |
| 승점 승률 | `(승 + 0.5 × 무) / 전체` |
| 승격 기준 | **60% 이상** |

봇이 무상태 결정론이고 시작 위치가 시드로 고정되므로 **승률은 확률이 아니라 하나의 고정된 숫자**다. 몇 번을 돌려도 같은 값이 나오며, 표본 크기나 우연에 대한 통계 논의가 필요 없다.

**이 60%는 이후 루프가 통과하지 못한다는 이유로 낮추지 않는다** (BRIEF §11-4).

승격 후 홀드아웃 시드 50개로 한 번 더 돌려 기록한다. 심사 승률과 홀드아웃 승률의 격차가 시드 과적합의 정도다.

역대 전 세대 라운드로빈은 승격 판정에 쓰지 않고, 마지막에 한 번만 돌려 히트맵으로 남긴다(시드 10개 × 좌석 교대 = 20경기/페어).

## 7. 진단기

핵심 정의는 **손실(loss)** 하나다.

```
loss(t) = max_d reach(방향 d 선택 후) − reach(실제 선택 후)

d             4방향 전부. 후진도 포함하며, 후진은 자기 벽이므로 reach = 0이 된다
reach(·)      해당 선택 이후 내 머리에서 flood fill로 센 도달 가능 칸 수.
              그 선택이 즉시 사망(맵 밖 · 기존 벽 · 상대 머리)이면 reach = 0
치명적인 수    loss(t)가 최대인 턴
```

`loss(t) ≥ 0`이 항상 성립한다 (실제 선택도 `d`의 후보 중 하나이므로).

이 정의 하나가 셋을 해결한다.

1. **반려 피드백** — 패배 경기에서 손실 상위 3개 수를 뽑아 에이전트에게 돌려준다
2. **자멸률** — "즉시 죽지 않는 대안이 있었는데 죽는 방향을 고른" 턴의 비율. 위 계산의 부산물이다
3. **발표 화면 하이라이트** — "이 순간 봇이 졌습니다"에 같은 값을 쓴다

구현 비용을 한 번만 낸다.

### 7.1 리포트 스키마

## 8. 기록

### 8.1 두 층으로 나눈다

| 층 | 위치 | 용도 |
|---|---|---|
| **원본 기록** | `records/` | 개발 중 진단, 재현 검증, §8 이력 |
| **발표 번들** | `web/public/data/` | 화면이 실제로 읽는 정적 JSON |

발표 번들은 `./gradlew record`가 원본에서 추려 생성한다. **프론트엔드는 정적 파일만 읽으므로 발표 당일 백엔드가 떠 있지 않아도 화면이 뜬다** — 서버 장애라는 위험 범주 자체가 사라진다(R4).

### 8.2 리플레이 스키마

```jsonc
{
  "schema": 1,
  "matchId": "gen07-vs-champion-seed12",
  "grid": { "w": 30, "h": 30 },
  "seed": 12, "swapped": false,
  "bots": [ { "id": "Gen07Bot", "start": [4,15],  "dir": "RIGHT" },
            { "id": "Gen12Bot", "start": [25,15], "dir": "LEFT"  } ],
  "moves": "RLRLRUUL…",                      // 턴당 2문자, 두 봇 인터리브
  "result": { "winner": 1, "turns": 187, "reason": "P0_HIT_OWN_WALL" },
  "metrics": {                                // 진단이 필요한 경기에만
    "reach": [[900,899,…],[900,898,…]],       // 봇별 · 턴별 도달 가능 칸 수
    "loss":  [[0,0,3,…],[0,12,0,…]],          // 봇별 · 턴별 손실 (§7)
    "occupancy": [0.42, 0.38],                // 봇별 (자기 벽 칸 수 / 900)
    "suicideRate": [0.00, 0.03] },            // 봇별 자멸 턴 비율 (§7)
  "hash": "sha256:…"
}
```

`moves`는 턴당 2문자(먼저 봇0, 다음 봇1)이며 사망을 초래한 마지막 이동까지 포함한다. 이렇게 인코딩하면 187턴 경기가 374바이트다. **리플레이를 선별하지 않고 전부 남긴다.**

### 8.3 이력 구조

```
records/gen-07/
  attempt-1/  bot.java  gate-report.json                        (반려: G3 시계 사용)
  attempt-2/  bot.java  gate-report.json                        (반려: G4 인덱스 초과)
  attempt-3/  bot.java  gate-report.json  championship.json     (반려: 48%)
  attempt-4/  bot.java  gate-report.json  championship.json     (승격: 63%)
```

**반려된 `bot.java`도 지우지 않는다.** 실패 횟수가 보이는 편이 발표에 유리하다(§8).

### 8.4 발표 번들

```
web/public/data/
  gallery.json        세대별 대표 경기 — 최종 챔피언 상대, 전 세대 동일 시드
  generations.json    세대별 지표 시계열 (생존 턴 · 점유율 · 자멸률 · 승률 · 시도 횟수)
  loop-history.json   세대별 attempt 이력 (통과/반려, 반려 사유)
  roundrobin.json     히트맵 매트릭스
  sources/            세대별 bot.java 원문 + 직전 세대 대비 diff
```

### 8.5 재현 검증

R1을 문서상의 약속이 아니라 실행 가능한 검사로 둔다. 모든 경기의 정규화된 이동 시퀀스를 SHA-256으로 해시해 저장하고, `./gradlew record --verify`가 전체를 재실행해 대조한다. 하나라도 다르면 실패다. **발표에서 R1을 주장할 때 이 명령의 출력이 곧 증거다.**

부수적으로, 결정론이므로 경기들을 병렬로 실행해도 결과가 바뀌지 않는다.

## 9. 화면 (C3)

### 9.1 메인 — 세대 갤러리

모든 세대가 **최종 챔피언**을 상대로 **같은 시드**에서 겨루는 경기를 **동시에 재생**한다. 앞 세대 패널은 몇 초 만에 멈춰 회색으로 죽고, 뒤로 갈수록 계속 돌며 격자를 빼곡히 채운다.

설명 없이 30초면 "뒤로 갈수록 잘한다"가 보인다. **R3을 화면 하나로 증명한다.**

패널 수는 세대 수에 따라 반응형으로 늘어난다 (12세대 → 3×4, 16세대 → 4×4).

### 9.2 발표 서사 순서

**결과를 먼저 보여주고 그 다음에 과정을 밝힌다.** 과정을 먼저 설명하면 비개발자가 따라올 이유가 없다.

| | 화면 | 무엇을 말하는가 | 증거 |
|---|---|---|---|
| 1 | 세대 갤러리 | "뒤로 갈수록 잘한다" — 설명 없이 30초 | **R3** |
| 2 | 개선 곡선 | 눈으로 본 것을 숫자로 확인 | R3, R2 |
| 3 | **루프 타임라인** | 세대별 시도를 O/X로, 반려 사유별 색 | **C2** |
| 4 | 세대별 코드 diff | "이번 세대는 무엇을 배웠나" | **C1**, §6 |
| 5 | 단일 경기 + 진단 | 기계가 실수를 어떻게 짚었나 | C2, R2 |
| 6 | 히트맵 · 과적합 격차 | 순환 우위와 심사/홀드아웃 승률 차 | 부록 |

3번이 발표의 진짜 주인공이다. 반려된 시도들이 빨간 칸으로 줄줄이 늘어선 화면이 "루프가 돌았다"의 가장 직접적인 증거다.

### 9.3 연출

- **라이트사이클 트레일** — 최근 지나온 칸일수록 밝게. 정지 화면에서도 진행 방향이 읽힌다
- **사망 순간** — 흰 플래시 한 프레임 → 패널 전체 회색조 전환
- **패널 하단 생존 턴 카운터** — 죽으면 그 값에서 고정. 갤러리가 그대로 순위표가 된다
- **색은 청/주황** — 색각 이상에서도 구분되고 프로젝터 대비에 강하다
- **발표자 컨트롤** — 재생/정지/속도/처음으로

렌더링 비용은 문제가 되지 않는다. 트론은 벽이 영구적이라 **캔버스를 지울 필요가 없다.** 매 프레임 새로 그리는 셀은 봇당 1칸, 12패널을 합쳐도 24칸이다.

## 10. 모듈 구조

```
arena-core         게임 엔진. 규칙·격자·턴 판정·리플레이 생성
                   의존: 없음 (순수 Java, Spring 없음)
                        ▲
       ┌────────────────┼────────────────┬──────────────────┐
       │                │                │                  │
arena-bots       arena-gate      arena-diagnostics    arena-tournament
Bot 인터페이스    관문 G1~G7       flood fill 진단기      대전·승격 판정
세대별 봇 구현    퍼징/벤치/검사    지표 계산            라운드로빈·기록 저장
베이스라인 봇          │                │                  │
       ▲───────────────┴────────────────┴──────────────────┘
                        │
                   arena-api
                   Spring Boot. 리플레이 서빙 + CLI 커맨드
```

**원칙 셋**

1. **`arena-core`는 Spring을 모른다.** 엔진이 순수 자바 함수라 테스트가 밀리초로 끝나고 R1 검증이 간단해진다.
2. **봇은 `GameView`와 `Direction`만 본다.** "무엇을 감출 것인가"가 규율이 아니라 **모듈 경계로 강제**된다.
3. **의존은 단방향.** 관문은 봇을 알지만 봇은 관문을 모른다. 봇이 관문의 존재를 알면 관문을 겨냥해 코드를 쓸 수 있다.

### 10.1 스택 (C4)

- **백엔드** Spring Boot — 게임 엔진, 관문, 루프 오케스트레이션, 진단기, 리플레이 생성 및 서빙
- **프론트엔드** Next.js (App Router) + TypeScript + Tailwind + Canvas

## 11. 테스트 전략

하네스가 곧 판정 인프라다. **하네스는 무엇이 판정하는가**에 답이 없으면 C1 전체가 신뢰를 잃는다.

### T1 — 엔진 규칙 (`arena-core`) · TDD

예제 테스트에 더해 속성 테스트 셋을 건다.

```
대칭성    play(A, B, seed)의 승자 == play(B, A, seed)의 승자를 뒤집은 것
종료 보장  임의의 봇 조합에 대해 경기는 900턴 이내에 반드시 끝난다
벽 단조성  W(t) ⊆ W(t+1)  이고  |W(t+1)| − |W(t)| == 생존 봇 수
```

### T2 — 관문 (`arena-gate`) · 함정 봇 스위트

각 관문마다 **일부러 그 관문을 위반하는 봇**을 fixture로 두고, 관문이 정확히 그 봇을 반려하는지 검증한다.

| 함정 봇 | 위반 | 반려해야 할 관문 |
|---|---|---|
| `StatefulTrap` | 인스턴스 필드 보유 | G2 |
| `ClockTrap` | `System.nanoTime()` 사용 | G3 |
| `CrashTrap` | 특정 국면에서 예외 | G4 |
| `NondeterministicTrap` | `Object.hashCode()` 순서에 의존 | G5 |
| `SlowTrap` | 의도적으로 무거운 연산 | G6 |
| `WeakTrap` | 벽회피봇에게 지는 수준 | G7 |

**관문을 추가하면 함정 봇도 함께 추가한다.** 이 스위트가 "관문이 진짜 작동하는지 어떻게 압니까?"에 대한 답이며 C1의 가장 강력한 증거다.

### T3 — 진단기 · TDD
손으로 만든 5×5 격자에서 `loss` 값이 손계산과 일치하는지 검증한다.

### T4 — 재현성 · CI
`./gradlew record --verify`를 CI에서 돌린다. **R1이 테스트로 존재한다.**

### T5 — 프론트엔드
발표 번들 JSON의 스키마 계약 테스트만 둔다. 시각 회귀 테스트는 두지 않는다.

## 12. 베이스라인 봇과 Gen 0

`arena-bots`의 `baseline` 패키지에 고정하고 **한번 커밋한 뒤로는 수정하지 않는다.** 기준이 움직이면 세대 간 비교가 무의미해진다.

| 봇 | 정의 | 대략적 강도 |
|---|---|---|
| `StraightBot` | 항상 현재 방향 유지 | 벽에 박아 죽음 (중앙 시작 기준 약 15턴) |
| `RandomBot` | 시드 있는 균등 4방향 | 후진 자멸로 평균 ~4턴 |
| `WallAvoidBot` | 즉시 죽지 않는 방향 중 고정 우선순위로 선택 (1수 앞만) | 위 둘을 압도 |

**Gen 0 = `StraightBot`.** 직선 하나가 그려지다 벽에서 멈추는 그림은 "얘는 아무 생각이 없다"가 즉시 전달된다. 또한 기준선이 약 15턴이므로 R3 합격선(10배)이 **150턴**이라는 의미 있는 값이 된다.

## 13. 파라미터

| 항목 | 값 |
|---|---|
| 격자 크기 | 30 × 30 |
| 최대 턴 | 900 (구조적 상한) |
| 목표 세대 수 | 12 (상한 아님 — 시간이 남으면 더 돌린다) |
| 심사 시드 | 1‥50 (× 좌석 교대 = 100경기) |
| 홀드아웃 시드 | 1001‥1050 |
| 라운드로빈 시드 | 심사 시드 중 1‥10 (× 좌석 교대 = 20경기/페어) |
| 승격 기준 | 승점 승률 60% |
| 무승부 배점 | 0.5 |
| 세대당 재시도 한도 | 5회 |
| G4·G5·G6 국면 수 | 10,000 |
| G6 응답 시간 상한 | p99 5 ms |
| R3 합격선 | Gen 0 대비 평균 생존 턴 수 **10배** |

**이 수치들은 루프가 통과하지 못한다는 이유로 낮추지 않는다** (BRIEF §11-4). 통과하지 못하면 봇이 부족한 것이다.
